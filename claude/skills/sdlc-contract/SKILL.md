# sdlc-contract — Public contracts before code (v4.0)

## SDLC integration

- **When to use:** in two steps. (1) During `/sdlc:plan`, when an A### exposes an
  API or events: `sdlc-architect` settles the contract decisions (the
  [contract sheet](assets/contract.md) helps) and records one row per contract in
  the **Interfaces / API** section of `2_architecture.md` (planned schema path,
  consumers, version, verifying T###). The architect writes nothing else.
  (2) During `/sdlc:dev`: a dedicated contract P### writes the schema file in the
  repository (OpenAPI, JSON Schema or a message contract), under Code Lock like
  any other code, before the P### that implement or consume it.
- **Deliverable:** the schema file (step 2) and the Interfaces row (step 1). The
  contract sheet settles decisions; it does not replace the schema.
- **Traceability:** the contract P### names the contract in its **Fixes
  contract** field; every implementing or consuming P### lists that P### in
  **Depends on**, so the wave planner orders them. Contract tests are `T###` of
  the implementing P###.
- **Verified by the gate:** no. The gate does not parse schemas. The proof is the
  validation command and the contract tests, recorded in `4_tests.md`.

## Method

Read the consumers, the existing schemas and the versioning conventions. Keep the
OpenAPI version already in use; check its official documentation when the syntax
is uncertain. A Markdown draft does not replace an executable specification when
the project expects OpenAPI.

Define methods, paths, parameters, required fields, bounds, enums, nullability,
responses and consistent examples. Keep **input and output DTOs separate** and
list the allowed fields explicitly. No production data in the examples.

Define authentication **and** authorization per operation and per resource; a
private network does not replace them. Define errors without internal traces,
pagination, limits and idempotence when relevant. A **202** means the request was
accepted, not that processing succeeded: specify how it is tracked and how later
failures are reported.

Assess breaking changes for consumers: removal, new required field, changed type
or status, extended enum depending on their tolerance. Document the migration or
versioning needed. Never expose another component's storage structure.

## Verification

Validate syntax, references and examples with the project's tools. Write tests
against the real implementation: success, invalid input, access denied and the
planned errors. Assertions target the public contract. Do not compare JSON
strings naively, and never use the schema generated by the implementation as an
independent oracle. For events, specify delivery, ordering, duplicates,
compatibility and replay.

Never claim "compliant" because a file parses. Report the contract, its
consequences for consumers, the tests actually run and the limits.
